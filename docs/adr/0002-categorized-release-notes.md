# ADR 0002: リリースノートの変更点を分類し、コミットへのリンクを付ける

ステータス: 採択

## 文脈

v0.0.2 までのリリースノートは、`scripts/release_notes.ts` が生成していた。
内容は、前のリリースの辞書と比べた (読み, 候補) の組の追加・削除・注釈の変更だけで、
スクリプトや文書、CI の変更は載らず、変更を行ったコミットへのリンクもない。

利用者の規則では、リリースノートは次のように書く。

- GitHub の Releases に置く
- 変更点を「追加」「変更」「削除」「修正」などの項目に分ける。必要ならほかの項目も足す
- 可能であれば、各変更を行ったコミット（または PR）を添える。リンクは絶対リンクにする
- リリースノート内の ADR はリンクにする
- 英語で書く

[ADR 0001](0001-adopt-adr-and-adr-guard.md) では、この書式への変更を別の ADR で扱うことにしていた。

ただし、このリポジトリは日本語の SKK 辞書であり、使うのは日本語話者だけである。
リリースノートを読むのも辞書の利用者なので、このリポジトリでは英語で書く規則の例外とし、リリースノートを日本語で書く。
コミットログは利用者の規則どおり英語で書く。

## 実装すること

### リリースノートの構成

リリースノートは日本語で書き、次の節をこの順に置く。中身のない節は書かない（「語彙」と「配布物」は常に書く）。

```markdown
## v0.0.3

[v0.0.2](https://github.com/tett23/SKK-JISYO.mahjong-riichi/releases/tag/v0.0.2) からの変更。

### 追加
- Add テンパイ料 and 牌姿 ([104ca2f](https://github.com/tett23/SKK-JISYO.mahjong-riichi/commit/104ca2f…))

### 変更
- Adopt ADR workflow and adr-guard ([ADR 0001](https://github.com/tett23/SKK-JISYO.mahjong-riichi/blob/v0.0.3/docs/adr/0001-adopt-adr-and-adr-guard.md)) ([4426e11](…))

### 削除

### 修正

### 語彙
- 収録数: 748 組（v0.0.2: 745 組）
- 追加: 3 組 / 削除: 0 組 / 注釈の変更: 0 組
- `[requested]`（L にない役名）: 72 組

<details><summary>追加した組（3 組）</summary> … SKK の行の形 … </details>
<details><summary>削除した組（0 組）</summary> … </details>
<details><summary>注釈を変えた組（0 組）</summary> … </details>

### 配布物
| ファイル | 内容 |
|---|---|
| `SKK-JISYO.mahjong-riichi` | 完全版（全収録） |
| … | … |
```

- 前のリリースがなければ、冒頭の文を「初回リリース。」にし、語彙ではすべての組を追加として載せる
- 追加・変更・削除・修正の各行は、コミットの件名（英語）をそのまま載せる

### コミットの分類

前のリリースのタグから今回のタグまでのコミット（マージコミットを除く）を、件名の最初の単語で分類する。

| 最初の単語（大文字小文字は区別しない） | 節 |
|---|---|
| `Add`、`Introduce`、`Create`、`Support` | 追加 |
| `Remove`、`Delete`、`Drop` | 削除 |
| `Fix`、`Correct` | 修正 |
| それ以外 | 変更 |

- 件名が `v` で始まる版番号だけのコミット（`v0.0.2` などのリリースの準備）は載せない
- 各行は件名の後ろに、短い SHA（7 桁）で `https://github.com/<owner>/<repo>/commit/<SHA>` へのリンクを付ける
- 件名に `(#123)` があれば、`https://github.com/<owner>/<repo>/pull/123` への絶対リンクに置きかえる
- 件名に `ADR NNNN` があれば、今回のタグの時点の `docs/adr/NNNN-*.md` への絶対リンク（`https://github.com/<owner>/<repo>/blob/<tag>/docs/adr/…`）に置きかえる。該当するファイルがなければ置きかえない
- 前のリリースがなければ、今回のタグまでのすべてのコミットを対象にする

### スクリプトとワークフロー

- `scripts/release_notes.ts` を、次の引数を取る形に変える

  ```
  release_notes.ts --tag <tag> --repo <owner/repo> --dict <今回の辞書> --commits <file>
                   [--prev-tag <tag> --prev-dict <前回の辞書>]
  ```

  `--commits` のファイルは 1 行 1 コミットで `<SHA>\t<件名>`。`git log --no-merges --format='%H%x09%s' <prev>..<tag>` の出力をそのまま使う。ADR のファイルの有無は作業ツリーの `docs/adr/` で調べる
- 分類・リンクの置きかえ・本文の組み立ては純粋な関数にし、ファイルやコマンドの入出力は `import.meta.main` の中に閉じる
- `.github/workflows/release.yml` は、`fetch-depth: 0` でチェックアウトし、前のリリースのタグからのコミットを `git log` で書き出して渡す。前のリリースの決め方は今までどおり（GitHub Releases の一覧で、今回のタグを除いた最新のもの）
- `docs/specifications.md` にリリースノートの節を立て、上の構成と分類、日本語で書く理由を書く。README の「リリース」の節も直す

## 実装しないこと

- 公開済みのリリース（v0.0.1-rc1 〜 v0.0.2）のリリースノートの書きかえ
- 件名の規約（`feat:` のような接頭辞）の導入。件名は今までどおり英語の自然な文で書き、最初の単語で分類する
- コミットの件名の日本語訳。英語の件名をそのまま載せる
- 語彙の組ごとに、その組を足したコミットを特定してリンクすること。手入力データの 1 行から長音展開や skk-dev/dict の取り込みで複数の組ができるため、対応が 1 対 1 にならない。コミットは追加などの節で示す

## テスト設計

`tests/release_notes_test.ts` に、実装の前に次のテストを書き、失敗させてから実装する。既存の `tests/lib_test.ts` のリリースノートのテストはこちらへ移す。

1. 分類: `Add …`→追加、`add …`→追加、`Introduce …`→追加、`Remove …`→削除、`Drop …`→削除、`Fix …`→修正、`Bump …`→変更、`シャボ…`（日本語の件名）→変更
2. 版番号だけの件名（`v0.0.2`、`v0.0.1-rc2`）は除かれ、`v2 support` のような件名は除かれない
3. コミットのリンク: `abcdef1234…\tAdd foo` が `- Add foo ([abcdef1](https://github.com/o/r/commit/abcdef1234…))` になる
4. PR のリンク: 件名の `(#12)` が `([#12](https://github.com/o/r/pull/12))` になる
5. ADR のリンク: ADR のファイル一覧に `docs/adr/0001-x.md` があるとき、`ADR 0001` が `[ADR 0001](https://github.com/o/r/blob/v1.0.0/docs/adr/0001-x.md)` になり、一覧にない `ADR 0099` はそのまま残る
6. 本文: 前のリリースがあるとき、冒頭が前のリリースへの絶対リンクを含む「… からの変更。」になり、空の節（例: 修正）は出力されず、語彙と配布物は出力される
7. 本文: 前のリリースがないとき、冒頭が「初回リリース。」になり、すべての組が「追加した組」に載る
8. 語彙の差分: 追加・削除・注釈の変更を (読み, 候補) の組で数える（既存のテストの内容を移す）

ワークフローは自動テストを書けないので、次のリリースのときに、Releases のノートが上の構成になっていること、コミットのリンクと ADR のリンクが開けることを確かめる。

## トレードオフ

- 利用者の規則（リリースノートは英語）から外れる。読み手が日本語話者に限られる辞書なので、読みやすさを優先する。コミットの件名は英語なので、ノートの中で日本語と英語が混ざる
- 最初の単語による分類は、件名の書き方しだいで外れる（例: `Make X optional` は変更になるが、実質は削除かもしれない）。接頭辞の規約にすれば正確になるが、件名の自由さを失い、既存の書き方とも合わない。外れた場合はリリース後に Releases のノートを手で直せばよいので、単純な規則を選ぶ
- 語彙の変更とコードの変更を同じリリースノートに載せるので、ノートが長くなる。語彙の一覧は `<details>` で畳み、要約の数だけを見えるようにする
- `--commits` をファイルで渡すことで、スクリプトは git に依存せずにテストできる。その代わり、ワークフローで `git log` の出力を作る手順が 1 つ増える
